# CRI server2

Go-сервер китайского радио с HLS, субтитрами, пиньинем и словарями. Сохраняет внешний протокол `server`, заменяя запуск модели на каждом фрагменте постоянно работающим SenseVoice-сервисом. [Утверждённая спецификация](SPEC.md), [результаты проверок](VALIDATION.md).

## Запуск

Нужны Docker с Compose, 4 vCPU и 8 ГБ RAM. Контейнеры вместе ограничены 6 ГБ RAM. Веса моделей и словари подключаются отдельно от образов.

```sh
cd server2
cp .env.example .env
```

В `.env` укажите абсолютные пути:

```dotenv
MODEL_ASSETS_DIR=/absolute/path/server/.docker-cache
ASR_MODEL_DIR=/absolute/path/server/.docker-cache/sense-voice-2024
HANLP_ASSETS_DIR=/absolute/path/hanlp-models
HTTP_PORT=8080
```

`MODEL_ASSETS_DIR` должен содержать `dabkrs.gz`, `cedict_ts.u8`, `zh-extract.jsonl.gz`, `Unihan_Readings.txt`. Каталог SenseVoice должен содержать `model.int8.onnx` и `tokens.txt`. Эти файлы уже используются старой сборкой; повторно скачивать их не нужно.

Для нового каталога HanLP один раз подготовьте ту же модель `COARSE_ELECTRA_SMALL_ZH`:

```sh
mkdir -p /absolute/path/hanlp-models
docker compose --profile prepare run --build --rm prepare-hanlp
docker compose up --build -d --wait --wait-timeout 600
docker compose ps
curl -f http://localhost:8080/health/ready
```

Первый запуск ждёт загрузки словарей и наполнения трёхминутного буфера. На системах с отдельным бинарником Compose замените `docker compose` на `docker-compose`. Подготовка HanLP требует интернета; сервисы распознавания во время работы используют внутреннюю сеть и готовые модели только для чтения. Существующий кеш HanLP также можно использовать, см. [инструкции сервисов](services/README.md).

Для параллельной проверки рядом со старым сервером выберите другой `HTTP_PORT`, например `18088`. При окончательном переключении освободите прежний порт и измените адрес сервера в Android при необходимости. Старую директорию и старый Docker volume эта версия не изменяет.

## Данные и восстановление

Именованный volume `archive` хранит `/data/archive.db` и аудио `/data/hls`. Перезапуск или обновление контейнера сохраняет историю и счётчик ID. `docker compose down` сохраняет volume; **`down -v` удаляет историю**.

Последние три часа — желаемая глубина хранения. По умолчанию записи ограничены 10 ГиБ, а на файловой системе оставляется резерв 10 ГиБ. Старейшие записи удаляются раньше срока при нехватке места. Если освободить место нельзя, приём приостанавливается и повторяется автоматически. Это не очищает логи и данные других приложений на хосте.

Незавершённая очередь ограничена пятью минутами и живёт в памяти/приватных аудиофайлах. Обрыв радиоисточника не уничтожает уже подготовленную очередь. При истечении срока или переполнении старейшие необработанные участки пропускаются. Перезапуск всего Go-сервера сохраняет опубликованные записи; незавершённые задания удаляются.

Звук становится доступен в HLS после успешного ASR и обработки текста. Ошибка модели не превращается в пустые «успешные» субтитры. Настоящая тишина допустима. `DELAY=180s` задаёт задержку публикации HLS; клиент добавляет собственный небольшой буфер воспроизведения.

Сбой модели не требует перезапуска Go. Процесс модели завершается по жёсткому таймауту и запускается заново политикой Compose. Предыдущий процесс обязательно завершается до новой загрузки модели.

## Протокол

Существующие маршруты сохранены:

- `/hls/playlist.m3u8`, `/hls/000000123.ts`;
- `/api/metadata/000000123.json`, `/api/metadata/index.json`;
- `/api/segments/range?start_sec=…&end_sec=…&limit=500&offset=0`;
- `/api/segments/at?sec=…`, `/api/segments/batch?last=3&lite=true`;
- `/api/subtitles` — SSE с событиями `sync` и `segment`;
- `/api/status` — состояние, границы архива, очередь, ошибки, занятый объём.

`/health/live` проверяет процесс, `/health/ready` — готовность воспроизведения и записи. При первом запуске готовность появляется после наполнения задержанного HLS-окна. Ожидание модели, буферизация, переподключение и нехватка места отражаются в статусе.

Для согласованного офлайн-скачивания первый запрос `/range` содержит `snapshot=create`. Ответ добавляет `snapshot_id` и `snapshot_expires_at` (UTC RFC3339). Последующие страницы и запросы аудио передают `snapshot=<id>`. Состав, порядок и `total` фиксированы на десять минут. Не более пяти снимков одновременно. `DELETE /api/snapshots/<id>` освобождает снимок досрочно. Истёкший снимок возвращает `410`, недостаток места — `503`, превышение ёмкости — `429`. Ограниченные ответы не обрезаются молча.

Для новых гарантий офлайна и синхронизации через пропуски установите обновлённое Android-приложение из соседней директории `android`. Старый клиент продолжает понимать базовые маршруты, но его прежние ошибки обработки разрывов и частичного скачивания остаются в старом APK.

## Архитектура и ограничения

Один ffmpeg одновременно выдаёт PCM в память и закрытые HLS-файлы. Время берётся из фактических длительностей/меток HLS, а не из `ID × 3`. Учитывается задержка MP3-кодировщика. Каждый опубликованный файл получает долговечный целочисленный ID; SQLite фиксирует метаданные только после записи аудио. Очистка учитывает снимки и активные передачи, а после аварии удаляет незавершённые файлы.

Модель SenseVoice и HanLP работают в отдельных сервисах с одним активным запросом каждый. Go не создаёт временные WAV и не запускает ASR CLI. Словари загружаются один раз; их существующая реализация и тесты сохранены. Индексы и запросы хранятся в SQLite, без перечитывания всех JSON на каждом запросе статуса.

Ограничены очередь, память контейнеров, процессы, соединения, запросы, размер аудио/JSON, длительность операций и журналы Docker. Публичного pprof и опубликованных портов моделей нет. При аварии данные могут отсутствовать в эфире, но это явный разрыв времени с автоматическим переходом Android, а не незаметное смещение субтитров.

## Проверки

```sh
go test -race ./...
go vet ./...
python3 -m unittest discover -s services -p 'test_resident.py'
CRI_TEST_ASSETS=/absolute/path/server/.docker-cache go test ./internal/pipeline -run TestDeploymentAssets -v
CRI_SOAK_SECONDS=600 go test -race ./internal/pipeline -run '^TestSoak$' -v -timeout=12m
```

Тесты с реальными ffmpeg запускаются при его наличии. Проверка моделей описана в `services/README.md`. Длительный тест использует настоящий ffmpeg и пять HTTP-клиентов, но детерминированный ASR; настоящее распознавание проверяется отдельно и в Docker-интеграции. Конкретные выполненные проверки и оставшиеся ограничения перечислены в `VALIDATION.md`.
